# coinex-match 启动流程

<div class="doc-lead">撮合引擎消费可交易委托，生成成交并驱动后续结算。</div>

工程目录：`coinex-match`。可运行应用：

| 模块 | 主类 | 形态 |
| --- | --- | --- |
| `matching-provider` | `MatchingEngineApp` | 非 Web + Dubbo，撮合核心 |
| `matching-admin` | `MatchingAdminApp` | Spring Web + Dubbo，管理端 |

另有 `matching-api`、`matching-es` 等支撑模块，不单独作为业务进程讲解。

## 职责边界

撮合负责在价格条件满足时产生成交；不负责用户登录，也不直接替代账务入账。启动时通常会从存储加载未完成委托进入内存订单簿（以工程 Mapper / Bootstrap 逻辑为准）。

代码侧可见对 account、market、coin、partner、user 等 API 的 Dubbo 引用，因此相关 Provider 应先可达。

## 前置依赖

| 依赖 | 说明 |
| --- | --- |
| Apollo | provider 与 admin 使用不同 AppId 与 namespace |
| Dubbo | 注册发现；默认 compose 端口 provider **20905**、admin **20906** |
| Redis / ES / MySQL / MQ | 由 Apollo 配置；provider 命名空间含 redis、es、dubbo 等 |

provider 另有重启 / 探活监听，默认端口 **3001**（`stop.sh` 对 `3001` 发 `ruok`；可用 `-Drestart.listener.port` 调整）。

## 启动步骤

<Flow :steps='["Apollo 与基础 Provider 就绪","mvn package","启动 matching-provider","按需启动 matching-admin","确认注册与订单簿加载"]' />

### 1. 构建

```bash
cd coinex-match
mvn clean package -DskipTests
```

### 2. 启动撮合核心

```bash
java -Dapollo.meta=<Apollo地址> -Denv=DEV \
  -jar matching-provider/target/matching-provider.jar
```

或使用 `matching-provider/src/bin/start.sh`。

### 3. 启动管理端（可选）

```bash
java -Dapollo.meta=<Apollo地址> -Denv=DEV \
  -jar matching-admin/target/matching-admin.jar
```

HTTP 端口来自 Apollo，不在仓库写死。

### 4. Docker

```bash
cd coinex-match/docker
cp .env.example .env
docker compose up -d --build
```

默认同时拉起 `matching-provider` 与 `matching-admin`。

## 启动后检查

| 检查项 | 通过标准 |
| --- | --- |
| 进程 | provider 初始化完成，无关键依赖错误 |
| 探活 | 对重启端口（默认 3001）探测符合运维脚本约定 |
| 注册 | Dubbo 可发现撮合服务 |
| 业务 | 已有对手盘时可产生成交；深度 / 成交变化可被行情侧感知 |

建议启动顺序（实践经验，非仓库强制文档）：基础设施与 Apollo → account / coin 等基础服务 → entrust、market → **match**。

业务上的撮合语义见[核心交易流程 · 撮合与成交](/pages/0705#match)。
