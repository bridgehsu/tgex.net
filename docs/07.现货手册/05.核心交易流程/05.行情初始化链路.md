# coinex-market 启动流程

<div class="doc-lead">行情启动后的核心是：先判断交易对数据从哪里恢复，再灌进内存，最后才对外推送。</div>

工程：`coinex-market` / `market-provider`。行情主加载在 `MarketManager` 的 `@PostConstruct`；Netty 与部分定时任务在 `StartExecuteUtil.invoke()`（`ApplicationRunner`）。本文只写**启动后业务准备**。

## 先建立正确预期

| 阶段 | 含义 |
| --- | --- |
| Spring ApplicationReady | Jetty / Dubbo / MQ 等框架级就绪 |
| PostConstruct 行情加载完成（热路径） | 内存中已有交易对、深度、K 线等，Dubbo 读行情基本可用 |
| Netty 日志「启动成功等待客户端连接」 | WebSocket 可连；冷启动时部分交易对仍可能在后台初始化 |
| `JOB_IS_START == true` | 外部 Job 触发的 K 线 / 核对任务才会真正执行 |

**Spring Ready ≠ Netty 已监听 ≠ 每个交易对深度都已齐。**

## 1. PostConstruct：行情主加载

### 1.1 轻量预热

`CacheManager.initThirdRate()`：从 Redis Hash 灌入第三方汇率到内存。与交易对 K 线无关，属于轻量准备。

### 1.2 `MarketManager.init()` — 先判断交易对数据源

调用 `cacheManager.isInitSuccess()`。名字像查询，实际是**尝试从 Redis 全量加载交易对行情**。

#### 路径 A：Redis 已有交易对（常见热重启）

条件：Redis 中交易对 Hash 有数据。

1. Dubbo `TradeTypeService.listAllEnabled()` 取启用交易对；若一个都没有则直接结束加载。
2. 从 Redis 解析交易对进内存表。
3. 初始化 ticker、委托盘相关结构。
4. 线程池对每个交易对 `loadRedisData`：深度、各周期 K 线、检查 K 线，并标记「有数据可推」。
5. 更新人气榜等附属缓存。
6. **主线程等待**各交易对加载完成（热路径在 PostConstruct 内基本阻塞到齐）。

热路径结束后，内存与 Redis 对齐，后续 `MarketManager.init()` 的冷启动分支不再执行。

#### 路径 B：Redis 没有交易对

1. 查 MySQL 备份表：
   - 有备份 → `initDataBase`：备份灌回 Redis + 内存，再删备份。
   - 无备份 → `initService` **冷启动**。
2. 冷启动大致：
   - `tradeManager.initTradeType()`：Dubbo `TradeTypeService.listAll()` → 写入交易对缓存；
   - 初始化第三方交易所对接缓存；
   - 对每个需本地维护的交易对，**异步** `initTradeData`：深度（可调 entrust 侧盘口）、K 线 / ticker（库表或生成）、成交历史。

冷启动时 PostConstruct **可能很快返回**，各交易对仍在后台线程初始化——会出现「端口已开、部分交易对深度仍空」的窗口。

## 2. ContextRefreshed：EventBus

把 K 线 Job、落库监听等注册到 EventBus。之后 Dubbo `MarketJobsServiceImpl` 才能把任务丢进本机异步执行。  
此时 Job 开关可能仍为关，真正执行要等到 `StartExecuteUtil` 打开 `JOB_IS_START`。

## 3. ApplicationRunner：推送与对外通道

### 3.1 `SendMessage`（先执行）

启动定时推送：

- 高频：按订阅向客户端推 depth / ticker / trade / kline；
- 低频：首页 ticker、排行榜。

此时 Netty 可能尚未 bind，无连接时任务空转，属正常现象。

### 3.2 `MarketApplication` → `StartExecuteUtil.invoke()`

同一调用链内顺序：

1. **`putJobIsStart()`**  
   打开本机 Job 开关。之后外部触发的创建 K 线、刷新开盘价、核对交易对等才会真正 `asyncFireEvent`。

2. **第三方行情定时同步**（延迟后周期执行）  
   对非自有平台对接的交易对拉 depth / trade。依赖前面已写入的交易对列表；列表仍空时前几轮可能无操作。

3. **异步启动 Netty**  
   `MarketServer.start()` bind 配置端口；与后续步骤并发，不阻塞等 bind 结束。

4. **`setCoinType()`**  
   Dubbo 拉币种、商户币种、交易对元数据进 `CoinPriceCache`，供展示名与折算。与 K 线主加载相互独立。

5. **其它定时任务**  
   商户币种折合人民币、定期刷新币种缓存、人气榜等。

## 4. 交易对加载与推送的关系

| 数据 | 主要来源 | 作用 |
| --- | --- | --- |
| 交易对列表 | Redis / 备份表 / `TradeTypeService` | 后续一切行情的主键集合 |
| 深度 | Redis 或冷启动调 entrust；运行中还有 MQ | 盘口 |
| 成交 / K 线 / Ticker | Redis protobuf、备份或 DB period | 曲线与最新价 |
| 推送触发标记 | 加载末尾写入 | `SendMessage` 决定推什么 |

运行期 MQ（如深度、成交消息）可能在 PostConstruct 尚未完全结束时到达，依赖写缓存逻辑的幂等与覆盖策略。

## 5. 就绪分层

| 层级 | 判断 | 能做什么 |
| --- | --- | --- |
| 框架 Ready | ApplicationReady | Dubbo / Jetty / MQ Consumer 起来 |
| 热路径行情就绪 | PostConstruct 加载完成 | RPC 读内存行情基本可用 |
| WS 可连 | Netty 启动成功日志 | 客户端可订阅 |
| Job 可驱动 | `JOB_IS_START` | 分布式任务会在本机执行 |
| 冷启动未齐 | 部分 `initTradeData` 仍在跑 | 部分交易对深度 / K 线暂时为空 |

运维心跳通常只检查 Redis 交易对列表是否可读，**不检查 Netty**。

## 6. 依赖

启动期常依赖：交易对服务、商户交易对、entrust 盘口（冷启动）、币种服务、第三方行情、报表人气等。
