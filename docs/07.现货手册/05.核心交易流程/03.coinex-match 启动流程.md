# coinex-match 启动流程

<div class="doc-lead">Spring 容器起来之后，撮合要先把交易对、费率、未完成委托恢复进内存，再按交易对开放接单。</div>

工程：`coinex-match` / `matching-provider`。主初始化在 `MatchingBootstrap.init()`（`@PostConstruct`）。本文只描述**启动后的业务准备**，不讲 Maven / Docker 运维命令。

## 先建立正确预期

| 说法 | 实际含义 |
| --- | --- |
| 进程 Started | Spring / Dubbo 已起来，不等于每个交易对都能下单 |
| `MatchingBootstrap.init()` 返回 | 元数据缓存已加载；各交易对恢复多在线程池里**异步**进行 |
| 某交易对可撮合 | 该 symbol 的引擎 `isRunning && isRev`，且未完结委托已挂回订单簿 |

全局 Disruptor 管道在 `MatchingEngineManager` **构造阶段**就会 `start()`；真正「按交易对接单」要等到该对恢复完成并 `startRev()`。

## 1. 全局撮合管道

`MatchingEngineManager` 构造时：

1. 创建 `RBTreeOrderBook`（依赖 Redis）。
2. 启动 LMAX Disruptor（事件链：`SaveOrderHandler` → `MatchingBusinessHandler`）。
3. 置 `isRunning = true`。

此后全局管道可写事件；若 Disruptor 未捕获异常或落库失败，会把 `isRunning` 置 `false`，对外表现为整站拒写。

## 2. `MatchingBootstrap.init()` 主流程

### 2.1 失败重试定时器

一进入 `init()` 就注册定时任务：约 **10 秒后首次执行，之后每 5 秒**，对 `engineInitFailSet` 中的交易对再次调用 `recoverRedisEntrust`。单个交易对首次恢复失败时不会立刻让整个 Spring 启动失败，但会进入重试集合。

### 2.2 LevelDB 路径

`setLevelDBPath()` 按操作系统选择路径并打开 LevelDB（历史迁移相关；现行主路径以 Redis 为准）。

### 2.3 同步刷 Redis → MySQL

调用 `moveService.redisMoveDB(true, false)`：

- **同步**把上次崩溃留在 Redis 队列里、尚未入库的 account / entrust / entrust_order 增量刷进 MySQL。
- 某类型失败会重试；多次失败可能把全局 `isRunning` 置为 `false`。

含义：先保证「上次没落完的账」尽量落完，再装交易对引擎。

### 2.4 加载交易对（关键）

`initTradeType()`：

1. Dubbo `TradeTypeService.listAll()` → `TradeCache`（平台交易对：symbol、买卖币等）。
2. Dubbo `PartnerTradeTypeService.listAllEnabled()` → `TradeCache`（商户启用交易对）。

没有交易对元数据，后面就无法按 symbol 建引擎、也无法恢复委托。**撮合启动后的第一步业务判断，就是交易对集合是否可用。**

### 2.5 用户与费率相关缓存

在商户列表 `PartnerService.selectAllIsEnable()` 基础上依次：

| 步骤 | 方法 | 写入 |
| --- | --- | --- |
| 禁交易用户 | `initDisableUser` | `UserStatusCache` |
| 平台币抵扣手续费 | `initUserDeductionFees` | `UserDeductionFeesCache` |
| 商户手续费分成 | `initPartnerExtractRate` | `PartnerExtractRateCache` |
| VIP 手续费 | `initVipUserFees` | `UserFeesCache` |

撮合成交计价时会读这些缓存；启动时先拉齐，避免首笔成交才去远程拼费率。

### 2.6 价格类缓存

| 步骤 | 来源 | 用途 |
| --- | --- | --- |
| `initCoinCnyPrice` | `PartnerCoinTypeService` + `TickerService.getCoinsCNYPrice` | 币种人民币价 |
| `initTradeLastPrice` | `MarketService.getAllTickerData` | 最近成交价 → `MatchingLastPriceCache` |

最近成交价用于撮合侧价格相关逻辑；依赖行情服务可达。

### 2.7 后台持续落库

`moveService.redisMoveDB(false, true)`：异步线程长期消费 Redis 落库队列，与后续引擎恢复并行。

### 2.8 按交易对初始化引擎

`initializeEngines()`：

1. 再读一遍 `TradeTypeService.listAll()`。
2. 看 Redis 键 `INIT_REDIS_KEY`：
   - 非 `TRUE`：走 **MySQL** 恢复未成交委托（`recoverEntrust`）。
   - 为 `TRUE`：走 **Redis** 热恢复（`recoverRedisEntrust`）。
3. 线程池对每个交易对调用 `initEngine(symbol, …)`；另有特殊通道 `else`（充值 / 提现 / 改账等非交易对事件）。
4. 个别交易对（如代码中的 `shibusdt`）会强制走 MySQL 路径。
5. 主线程只等到「任务已提交」，**不等待每个 symbol 恢复完成**。

单个交易对 `initMatch` 大致：

1. `addEngine` 创建 `MatchingEngineProcessor`（processor 级 `isRunning=true`）。
2. `stopRev()`：此时对外下单 / 撤单会因未恢复完成被拒绝。
3. 恢复未完结委托（见下节）。
4. 成功则 `startRev()`，并从失败集合移除；失败则加入 `engineInitFailSet`。

### 2.9 高频策略缓存

`initHfTradeStrategy()`：按配置从 Redis 恢复当日高频卖单相关计数（若环境启用）。

### 2.10 异常

`init()` 主流程任一步抛错会向上抛出，可能导致 Spring 启动失败。单交易对恢复失败走重试集合，不必然拖垮整个进程。

## 3. 未完结委托如何挂回订单簿

### Redis 热恢复（`recoverRedisEntrust`）

1. 读该 symbol 在 Redis 中的未完结委托。
2. 首次初始化时顺带 pipeline 拉相关用户币币资产进 `UserBBAccountCache`。
3. 每条委托以 `INIT_MATCH`（或第三方类型）事件进入 Disruptor：
   - `SaveOrderHandler` 写入委托缓存；
   - `MatchingBusinessHandler` → `orderbook.enterInit` 挂簿。
4. 最后一条带 `initCompleted` 时推送深度；无委托则发初始化深度消息。
5. `startRev()`。

### MySQL 冷恢复（`recoverEntrust`）

1. `MatchingEntrustApi.queryNoTradeEntrustBySymbol` 查状态为未成交 / 部分成交的委托。
2. 批量加载涉及用户的币币钱包，写入缓存与 Redis。
3. 同样 `publishInit` 挂簿，再 `startRev()`。

## 4. 启动后「就绪」分层

| 层级 | 条件 | 能做什么 |
| --- | --- | --- |
| 全局管道 | `MatchingEngineManager.isRunning` | Disruptor 可处理事件 |
| 元数据就绪 | `TradeCache`、费率、价格缓存已装 | 具备按规则计价的前提 |
| 单交易对就绪 | `processor.isRunning() && isRev()` | 该对可接受下单 / 撤单 |
| 仍可能未完成 | 部分 symbol 在 `engineInitFailSet` 重试 | 这些对暂时拒单 |

运行期还有定时任务刷新交易对与分成、汇率等；启动不是一次性装完就再也不变。

## 5. 依赖的其它服务

启动期会通过 Dubbo 拉：商户、交易对、用户状态、手续费 / VIP、行情 ticker、CNY 价等。  
建议在 account、币种 / 交易对基础数据、market 至少部分可用后再看撮合是否「按对就绪」。

业务上的撮合语义见[业务流程 · 撮合与成交](/pages/070501#match)。账务与委托侧启动见[coinex-account 启动流程](/pages/070504)、[coinex-entrust 启动流程](/pages/070502)。
