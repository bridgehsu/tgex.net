# 充提改账协同

<div class="doc-lead">链上充提、人工调账等由账务侧发起；要影响现货交易可用余额，必须进入撮合改账通道，与下单 / 成交 / 撤单争同一份热钱包。本页只写**与撮合的协同**，不写钱包扫块与审核细节。</div>

链上出入金步骤见[钱包 · 核心充提流程](/pages/1003)；划转 / 冻结语义见[核心资金流程](/pages/0602)；撮合热钱包结构见[用户币币账户缓存](/pages/070802)。

## 为什么必须进撮合

现货 V1 下，**交易当下可用 / 冻结的权威在撮合进程内存**。若充提只改 MySQL 或只改账务库、不通知撮合：

- 用户已到账，交易页仍显示旧可用 → 误拒单  
- 或页面已加钱、撮合未加 → 可能超卖占用  

因此架构图上的「余额同步」虚线，指的是：**账务事实 → 消息 → 撮合改账事件 → 热缓存**。

## 协同路径

```
充提 / 调账在账务侧确认
    → 消息队列（或等价通知）
    → 撮合非交易对改账通道
    → 与该用户币种相关的事件串行处理
    → 改写用户币币账户缓存（可用增减等）
    → 异步落缓冲 / 流水旁路
```

要点：

1. **不挡下单主链**：用户点下单时，不会先同步堵在账务「充提完成」接口上；到账是旁路对齐。  
2. **与交易事件同链串行**：改可用与挂单冻结抢同一格子，避免「一边充值加可用、一边下单冻可用」交叉写花。  
3. **装入只补洞**：格子已在内存则以内存为准；缺失时才回源，见账户缓存文档。

账务服务自身如何就绪（在线改账、批处理扫流水），见[账务初始化链路](/pages/070506)。

## 和交易主路径的关系

| 路径 | 谁改热钱包 | 是否占订单簿 |
| --- | --- | --- |
| 下单冻结 / 成交划转 / 撤单解冻 | 撮合交易事件 | 是（下单 / 撤单） |
| 充提到账 / 调账 | 撮合改账事件 | 否 |
| 手续费暂存累计 | 成交事件内 | 间接（随成交） |

页面上「余额变了」可能来自充提到账，也可能来自成交或撤单；权威仍以撮合热缓存（协同完成后）为准。对账层次见[对账与资金一致性](/pages/0603)。
