撮合初始化链路 ​

撮合系统进程起来之后，撮合要先准备好交易对和计价规则，再按交易对把未完结委托挂回盘口，最后才对该交易对开放下单与撤单。

对应工程：tgex-match。下文只讲业务准备顺序，不展开类名与接口细节。

先分清两层就绪 ​

状态含义
进程已起来服务可注册、全局撮合通道可用，不等于每个交易对都能下单
某交易对已开放该交易对的未完结委托已恢复进订单簿，可以接受新的下单 / 撤单

常见情况：元数据装完后，各交易对仍在并行恢复；有的对已经开放，有的对还在重试。

总流程 ​

1. 全局通道先就绪 ​

撮合进程启动后，会先准备好全局事件通道和订单簿基础设施（依赖 Redis）。
此时整站可以处理内部事件；若后续「未落库数据刷库」多次失败，可能把全局通道关掉，表现为暂时整站拒写。

2. 先刷未落库数据 ​

启动时会同步处理：上次异常停机留在 Redis 队列里、尚未写入 MySQL 的增量（账户变动、委托、委托明细一类）。

目的：先把「上次没落完的账」尽量落完，再恢复各交易对盘口，避免内存状态和库不一致。

刷完后，会另起后台任务持续消费 Redis → 数据库，与后面的按交易对恢复并行。

3. 加载交易对（关键） ​

从交易对 / 商户相关服务拉取：

数据来源（工程侧）用途
平台交易对币种 / 交易对配置服务知道有哪些 symbol、买卖币
商户启用交易对商户交易对服务哪些商户开了哪些对

没有可用交易对，后面无法按对恢复委托，也无法开放接单。
所以初始化链路里，交易对集合是否拉到，是第一道业务门槛。

4. 装入规则与价格缓存 ​

在启用商户列表基础上，继续从用户、账务、商户、行情等服务装入内存规则：

内容大致来源用途
禁止交易的用户用户状态类服务恢复后下单仍要拦截
平台币抵扣手续费账务 / 手续费配置成交计价
商户手续费分成商户服务分成计算
VIP 手续费用户 / VIP 服务成交计价
币种人民币价商户币种 + 行情计价展示与折算相关
各交易对最近成交价行情服务撮合侧价格参考

这些在启动时先拉齐，避免「第一笔成交才去拼费率」。

5. 按交易对恢复委托 ​

拿到交易对列表后，对每个交易对（并行）走恢复：

从哪里读未完结委托 ​

由 Redis 中的「是否已热启动过」一类标记决定主路径：

路径数据来源适用
热恢复Redis 中该交易对未完结委托常见重启，盘口还在缓存里
冷恢复MySQL 中未成交 / 部分成交委托首次或标记要求走库

个别交易对可能被配置为始终走数据库路径。
另有一条非交易对通道（充值、提现、改账等内部事件），不挂普通买卖盘。

热恢复时大致做什么 ​

  1. 从 Redis 读出该交易对未完结委托。
  2. 需要时补齐相关用户的币币资产快照（Redis / 账务侧数据）到本地缓存。
  3. 把委托逐笔挂进该交易对订单簿。
  4. 推送或刷新深度。
  5. 开放该交易对接单。

冷恢复时大致做什么 ​

  1. 按交易对从数据库查出未完结委托（会结合商户交易对信息）。
  2. 批量补齐涉及用户的钱包缓存。
  3. 同样挂簿，再开放接单。

失败与重试 ​

某个交易对恢复失败时：

  • 通常不会拖垮整个进程；
  • 该对进入失败集合，定时重试（先等一段时间，再周期性重试）；
  • 重试成功前，该对对外下单 / 撤单应被拒绝。

主流程只保证「各交易对恢复任务已提交」，不保证全部交易对同一时刻都已开放。

6. 其它附属准备 ​

若环境启用高频相关策略，还会从 Redis 恢复当日卖单计数一类辅助数据。
运行期仍会定时刷新交易对、分成、汇率等——初始化不是装完就再也不变。

7. 就绪怎么理解 ​

层级大致条件能做什么
全局通道进程正常且未因刷库失败关停内部事件通道可用
规则就绪交易对、费率、价格等已进内存具备按规则处理的前提
单交易对开放该对委托已挂簿且已开放接单可接受该对下单 / 撤单
部分未完成仍在失败重试这些对暂时不可交易

8. 依赖哪些其它工程 / 中间件 ​

类型用途
Redis未落库队列、热委托、资产快照、启动标记
MySQL冷恢复委托、刷库落库目标
交易对 / 商户服务交易对清单
用户服务禁交易、VIP
账务相关服务手续费抵扣、钱包快照
行情服务最近价、人民币价

建议：账务、交易对基础数据、行情至少部分可用后，再观察撮合侧「按交易对是否已开放」。

业务上的撮合语义见业务流程 · 撮合与成交。同组：委托初始化链路、账务初始化链路、行情初始化链路。
